# Как создать и развернуть новый навык LegalOS

> Пошаговая инструкция для нового разработчика.
> Актуальный путь: `chat-service → native-orchestrator → MCP-навык`.
> Эталон каркаса сервиса: `rnd/savva`. Рабочий пример MCP и CI/CD: `l3m/backend/land_area`.

> **Критически важно:** наличие `chat-service` в схеме запроса не означает, что его нужно менять при
> подключении нового MCP-навыка. До отдельного архитектурного решения и согласования с владельцами
> сервиса **не изменяйте никакие файлы, URL или переменные `chat-service`**, включая
> `orchestrator_client__base_url` и `orchestrator_client_v2__base_url`. Регистрация нового навыка
> выполняется на стороне согласованного native-orchestrator. Переключение общего chat-service на
> другой deployment оркестратора уже приводило к поломке ГПН — общего потребителя прежнего маршрута —
> и потребовало срочного revert.

Полезные репозитории:

- [savva — эталон каркаса](https://gitlab.gigalegal.space/rnd/savva);
- [chat-service](https://gitlab.gigalegal.space/l3m/backend/chat-service);
- [native-orchestrator](https://gitlab.gigalegal.space/l3m/backend/native-orchestrator);
- [land_area — рабочий пример навыка](https://gitlab.gigalegal.space/l3m/backend/land_area);
- [2-ndfl-analysis — пример настройки сервиса и Vault](https://gitlab.gigalegal.space/l3m/backend/2-ndfl-analysis);
- [s3_service — загрузка и обработка файлов](https://gitlab.gigalegal.space/l3m/backend/s3_service);
- [depermash — обезличивание данных](https://gitlab.gigalegal.space/l3m/backend/depermash).

## Что получится в конце

После выполнения инструкции у вас будет:

- отдельный репозиторий навыка;
- качественный Python-сервис с тестами, логами, healthcheck и метриками;
- MCP endpoint, который видит native-orchestrator;
- автоматический деплой на DEV-стенд;
- карточка навыка, которую native-orchestrator получает из `SKILL.md`;
- доступ для тестового пользователя;
- пройденный сквозной тест через интерфейс LegalOS;
- репозиторий, готовый к переносу в Sigma.

## Общий порядок

Идите строго сверху вниз:

1. Получить доступы и выбрать имя навыка.
2. Создать репозиторий из `savva`.
3. Заложить Dynaconf и файловый контур S3 + depermash локально, без боевых секретов.
4. Реализовать сервис.
5. Реализовать MCP-интерфейс по примеру `land_area`, но пока нигде его не регистрировать.
6. Проверить сервис локально.
7. Настроить Docker и CI/CD.
8. Попросить Дмитрия Тихонова подготовить namespace/Vault и создать секреты.
9. Локально прогнать навык с реальными LLM, S3 и depermash через кастомную UI.
10. Поднять review-стенд и проверить его.
11. Смержить навык в `main` и проверить постоянный DEV-стенд.
12. Только теперь зарегистрировать MCP-адрес в native-orchestrator.
13. Не менять `chat-service`; использовать согласованный маршрут общего стенда.
14. Выдать пользователю доступ.
15. Проверить навык через UI стенда коллег.
16. Завершить DEV-приёмку.
17. Перенести сервис в Sigma по приложенной инструкции.

- SSH-доступ к `gitlab.gigalegal.space`;

## Шаг 2. Клонируйте `savva` и подключите новый репозиторий

Клонируйте эталон:

```bash
git clone git@gitlab.gigalegal.space:rnd/savva.git my-skill
cd my-skill
```

Переименуйте исходный remote, чтобы случайно не отправить изменения в `savva`:

```bash
git remote rename origin savva
git remote add origin git@gitlab.gigalegal.space:l3m/backend/my-skill.git
git remote -v
```

Создайте рабочую ветку:

```bash
git switch -c feat/initial-skill
```

Что заменить в шаблоне:

- название и описание проекта в `pyproject.toml`;
- `APP_NAME`, `MODULE_NAME` и безопасные настройки в TOML;
- старые названия `etalon_service`/`savva` в коде и документации;
- имя Dockerfile;
- `REPO_NAME`, `SERVICE_NAME`, `NAMESPACE`, hostname в CI/CD и Helm values;
- примеры запросов и ответы эталонного навыка.

Не удаляйте полезный каркас `savva`: app factory, Dynaconf, обработку ошибок, `structlog`, Prometheus, тесты, `Makefile`, Dockerfile и CI-гейты.

Результат шага: сервис запускается под новым именем и больше не связан push-доступом с `savva`.

## Шаг 3. Заложите конфигурацию и файловый контур без боевых секретов

Этот шаг выполняется до основной бизнес-логики, но обращаться к DevOps за регистрацией и токенами пока не нужно. Сначала навык должен хотя бы базово заработать локально.

### 3.1. Подготовьте Dynaconf и имена переменных

Используйте рабочую схему из `2-ndfl-analysis` и `land_area`. В `pyproject.toml` должна быть реальная зависимость с Vault-поддержкой:

```toml
"dynaconf[vault]>=3.2.13"
```

В конфигурации сервиса:

- включите загрузку TOML, `.env` и окружения через Dynaconf;
- заранее задайте собственный `ENV_FOR_DYNACONF`, совпадающий с будущим путем навыка в Vault;
- читайте вложенные ENV через двойное подчёркивание, например `LLM__MODEL`;
- добавьте в `.env.example` только названия переменных и безопасные примеры;
- локальный `.env` добавьте в `.gitignore`;
- не храните в коде API key, token, password, `change-me` и временные URL как рабочие значения.

Для совместимой с `land_area` настройки RouterAI используйте:

```text
LLM__PROVIDER=openai
LLM__MODEL=<согласованная модель>
OPENAI_BASE_URL=https://routerai.ru/api/v1
OPENAI_API_KEY=<секрет: ключ RouterAI>
```

Название `OPENAI_API_KEY` здесь связано с OpenAI-совместимым клиентом; фактически это ключ RouterAI. В коде и Vault имя переменной должно совпадать. Сам ключ новому сотруднику выдаёт Евгений Добрецов при первом подключении Claude, Codex или RouterAI.

На локальном этапе используйте mock/fake-клиенты и синтетические данные. Если личный RouterAI-ключ уже выдан, его можно положить только в локальный `.env`. Не запрашивайте боевые Vault-токены ради сервиса, который ещё не проходит базовый сценарий.

Добавьте понятную проверку обязательных настроек: при реальном запуске без URL или ключа приложение должно завершиться с явной ошибкой, а не возвращать пользователю стандартный ответ «Недостаточно данных». В unit-тестах настройки можно подменять.

### 3.2. Для файлового навыка сразу заложите S3 + depermash

Архитектуру хранения и обезличивания определите до бизнес-логики, даже если первый локальный прогон выполняется через fake-клиент:

```text
Пользователь → chat-service → S3 → текстовый слой + depermash
                               ↓
                    обезличенный текст по file_id
                               ↓
                         MCP-навык → LLM
                               ↓
                chat-service → деобезличенный ответ
```

> **Текущее ограничение:** действующий контур не распознаёт текст с изображений. Он извлекает уже существующий текстовый слой документа и передаёт его в depermash. Поэтому фотографии документов, сканы и PDF без текстового слоя пока не подходят. Обычные PDF-выписки и другие документы с выделяемым/копируемым текстом читаются и обезличиваются нормально.

Правила:

- файл загружается в S3, а не сохраняется на диске или в БД навыка;
- S3 извлекает текстовый слой и запускает обезличивание через depermash;
- до загрузки пользовательского файла проверяйте, что в нём можно выделить и скопировать текст;
- для фотографии или скана без текстового слоя возвращайте понятное сообщение о неподдерживаемом формате, а не результат «Недостаточно данных»;
- навык принимает `file_ids` и скачивает только `/s3/download/{file_id}/anonymized`;
- состояния `202`, `404` и `422` обрабатываются явно;
- один `chat_id` используется при загрузке, вызове chat-service и как `thread_id` навыка;
- сырой текст, ПДн и полный документ не пишутся в логи и не отправляются в LLM;
- ответ возвращается так, чтобы chat-service мог выполнить деобезличивание.

Сразу предусмотрите настройки, но пока без реальных значений секретов:

```text
S3_SERVICE_BASE_URL
S3_SERVICE_ACCESS_TOKEN
ANONYMIZER__BASE_URL           # если навык вызывает depermash напрямую
```

Прямой клиент depermash нужен не всегда: в стандартном файловом потоке обезличивание делает S3. На раннем этапе зафиксируйте интерфейс S3-клиента, обработку статусов, запрет локального хранения и тесты на fake-клиенте. Настоящий прогон S3 + depermash выполняется после подготовки инфраструктуры и создания секретов в Vault.

Результат шага: контракт настроек и файлового потока определён, код можно проверять локально без боевых токенов, а последующее подключение S3 и depermash не потребует переделывать архитектуру.

## Шаг 4. Реализуйте сам навык

Разложите код по слоям:

- `src/app` — HTTP и MCP-входы;
- `src/agents` — бизнес-пайплайн и работа с LLM;
- `src/infrastructure` — клиенты S3, depermash и других сервисов;
- `src/common` — конфигурация, ошибки, логи и метрики;
- `tests` — unit- и integration-тесты.

Обязательные свойства качественного сервиса:

- `GET /health` возвращает 200 и `{"status":"ok"}`;
- `/metrics` отдаёт Prometheus-метрики;
- ошибки пользователю понятны, traceback и технические переменные в ответ не попадают;
- секреты и ПДн не попадают в логи;
- настройки читаются из Dynaconf, секреты — из ENV/Vault;
- внешние запросы имеют timeout;
- LLM-ответы валидируются схемой, если от них ожидается структура;
- бизнес-логика тестируется без реальных внешних API;
- сервис не хранит состояние между запросами, если отдельное хранилище не согласовано архитектурно.

Если навык работает с файлами:

- принимайте `file_ids` от оркестратора;
- получайте из S3 обезличенный текст, а не сырой документ с ПДн;
- корректно обрабатывайте состояния «файл ещё готовится», «не найден» и «не распознан»;
- используйте `thread_id` как идентификатор текущего чата.

Результат шага: бизнес-сценарий работает локально и покрыт тестами.

## Шаг 5. Реализуйте MCP-интерфейс по примеру `land_area`

`savva` задаёт структуру сервиса, но полного MCP-примера в нём нет. Для интеграции с native-orchestrator смотрите:

- `land_area/src/app/mcp/`;
- `land_area/src/skills/land_area/SKILL.md`;
- `land_area/tests/integration/test_mcp.py`;
- mount `/mcp` и lifespan в `land_area/src/app/server/server.py`.

Что нужно добавить в свой сервис:

1. Зависимость `fastmcp` и обновлённый `uv.lock`.
2. Папку `src/app/mcp/` с MCP server и вызовом бизнес-сервиса.
3. Папку `src/skills/<skill_id>/SKILL.md`.
4. MCP tool с именем `<skill_id>_invoke`.
5. Mount MCP-приложения на `/mcp`.
6. Запуск lifespan MCP вместе с FastAPI.
7. Интеграционные тесты discovery и вызова tool.

Минимальный заголовок `SKILL.md`:

```yaml
---
name: my_skill
title: Человекочитаемое название
description: Когда выбирать навык, какой вход ему нужен и какой результат он возвращает.
mode: entrypoint
tool_name: my_skill_invoke
---
```

Для обычного навыка, который сам формирует итоговый ответ, используйте `mode: entrypoint`. Режим `agentic` нужен только сервисам с несколькими инструментами, которыми должен управлять native-orchestrator.

В параметрах tool объявите только то, что действительно используете:

- `thread_id`;
- `history_messages`;
- `file_ids`, если навык работает с файлами;
- `message_id`, если он нужен для ответа.

Native-orchestrator подставит эти значения сам. На MCP-границе поле называется `file_ids`.

Во время работы tool может отправлять короткие статусы и финальный человекочитаемый ответ. Не отправляйте клиенту внутренние переменные, сырые модели, stack trace или технический JSON.

На этом этапе вы только реализуете и локально тестируете MCP-контракт. Не добавляйте URL навыка в native-orchestrator и не меняйте `chat-service`: сервис ещё не проверен с реальными внешними сервисами.

Результат шага: локальный MCP возвращает resource `skill://my_skill/SKILL.md`, tool `my_skill_invoke` и корректный ответ, но навык ещё нигде не зарегистрирован.

## Шаг 6. Проверьте сервис локально

Установите зависимости и прогоните все обязательные проверки:

```bash
uv sync
make check
```

`make check` должен включать:

- lint;
- проверку форматирования;
- mypy;
- pytest;
- проверку границ импортов.

Запустите приложение:

```bash
make run
```

Проверьте:

```bash
curl -fsS http://localhost:8080/health
curl -fsS http://localhost:8080/metrics >/dev/null
```

MCP проверяйте не обычным `curl`, а FastMCP Client или интеграционным тестом. Должны успешно выполняться:

- `list_tools()`;
- `list_resources()`;
- чтение `skill://<skill_id>/SKILL.md`;
- вызов основного tool;
- сценарий ошибки пользователя.

Не переходите к деплою, пока `make check` не зелёный. Для первого прогона допустимы mock/fake-клиенты, синтетический документ и личный локальный ключ, если он уже выдан. Боевой Vault на этом этапе не требуется.

Убедитесь хотя бы в следующем:

- сервис запускается и отвечает на `/health`;
- MCP discovery и основной tool работают;
- бизнес-сценарий доходит до осмысленного результата, а не всегда возвращает заглушку;
- ошибки S3, LLM и входных данных обрабатываются предсказуемо;
- тесты подтверждают, что исходный файл и сырой текст с ПДн не сохраняются навыком.

Только после этого обращайтесь к Дмитрию Тихонову за подготовкой namespace, Vault policy и доступом к Vault. В QA навык пока не передавайте: реальный S3 + depermash и вызов LLM ещё нужно проверить с боевыми настройками.

Результат шага: локальный сервис и MCP работают, поэтому можно запрашивать инфраструктуру и секреты без риска настраивать их для неработающего прототипа.

## Шаг 7. Настройте Docker, Helm и GitLab CI/CD

Используйте актуальные файлы `land_area` как образец, заменив имена на свои:

- `.gitlab-ci.yml`;
- `ci_cd/dev/<service>.Dockerfile`;
- `ci_cd/run_scripts/start.sh`;
- `ci_cd/values.yaml`;
- `ci_cd/values-beta.yaml`.

Dockerfile должен:

- использовать Python 3.13 из доступного внутреннего registry;
- устанавливать зависимости через `uv sync --frozen --no-dev`;
- копировать весь `src`, включая `src/skills`;
- запускать приложение не от root;
- слушать порт из `PORT`, по умолчанию 8080.

В Helm values должны быть:

- `service.port`;
- ingress host и TLS;
- Dynaconf/Vault config;
- `ServiceMonitor` для `/metrics`;
- liveness/readiness probes на `/health`.

В pipeline нужны стадии:

1. quality — lint, typecheck, tests, import boundaries;
2. build — сборка образа Kaniko;
3. deploy — установка через общий `helm-general`;
4. remove — удаление review-стенда;
5. beta/RC — ручной деплой из `main`, если он нужен проекту.

Проверьте, что проект наследует:

- `DOCKER_AUTH`;
- `L3M_YC_REGISTRY`;
- `L3M_YC_KUBECONFIG`;
- `PROD_YC_KUBECONFIG`, если нужен beta/RC.

Если имя репозитория содержит `_`, задайте безопасный `INSTANCE_NAME` в `kebab-case`. Иначе Helm release или review hostname может не создаться.

Результат шага: pipeline может проверить, собрать и развернуть сервис без ручного изменения файлов.

## Шаг 8. Подготовьте инфраструктуру у DevOps и создайте секреты в Vault

Переходите к этому шагу только после успешного локального прогона. Здесь DevOps готовит namespace, Vault policy и доступы для будущего pod. Это ещё не регистрация навыка в native-orchestrator и не публикация навыка пользователям.

Напишите Дмитрию Тихонову и передайте четыре параметра:

- имя сервиса;
- Kubernetes namespace;
- права Vault-токена для pod: обычно только чтение;
- окружение: `main` или `beta`.

Готовый текст сообщения:

```text
Дмитрий, привет! Зарегистрируй, пожалуйста, новый навык:
- имя сервиса: my-skill
- namespace в Kubernetes: my-skill
- токен для pod: только чтение
- окружение: main
```

Для `land_area` запрос выглядел так:

```text
land-area — имя сервиса и namespace
для pod только чтение
main
```

Если нужен контур `beta`, укажите его отдельным запросом. Не считайте доступ `main` автоматически действующим в `beta`.

После подтверждения подготовки инфраструктуры попросите отдельный временный доступ для себя:

```text
А можешь дать токен с правами редактирования Vault на main?
```

Здесь используются два разных токена:

- **токен pod с правами только чтения** — нужен запущенному сервису; DevOps подключает его в Kubernetes через Secret `vault-token-for-dynaconf`;
- **токен человека с правами редактирования** — нужен разработчику только для входа в Vault и создания секретов.

Редакторский токен нельзя класть в код, `.env`, Helm values, Kubernetes-конфигурацию или переменные приложения. Не отправляйте его в MR, задачу, чат или логи.

### Как создать секреты навыка

1. Откройте [Vault DEV](https://vault-dev.gigalegal.tech/ui/vault/auth?with=token).
2. Вставьте полученный редакторский токен в поле авторизации по Token и войдите.
3. Перейдите в `secrets` → `dynaconf`.
4. Создайте хранилище/путь с техническим именем навыка, например `land-area`.
5. Убедитесь, что значение `ENV_FOR_DYNACONF` в Helm values **точно совпадает** с этим именем.
6. Добавьте необходимые секреты без кавычек и лишних пробелов.

Для навыка по образцу `land_area` минимальный набор такой:

```text
OPENAI_API_KEY=<ключ RouterAI>
S3_SERVICE_ACCESS_TOKEN=<токен S3-service>
```

`OPENAI_API_KEY` выдаёт Евгений Добрецов при первом подключении Claude, Codex или RouterAI. Хотя переменная называется `OPENAI_API_KEY`, в этой схеме в ней хранится RouterAI-ключ; запросы идут через `OPENAI_BASE_URL=https://routerai.ru/api/v1`.

`S3_SERVICE_ACCESS_TOKEN` новичок может взять из секрета `land-area`, если у него есть разрешённый доступ. Копируйте значение только внутри Vault: не переносите его через исходный код, MR, документацию или общий чат. Если доступа к исходному секрету нет, запросите токен у Дмитрия.

Добавьте и другие секреты, которые действительно использует сервис. Несекретные URL, название модели и безопасные флаги храните в TOML/Helm values, а не дублируйте без необходимости в Vault.

Проверьте, что `ENV_FOR_DYNACONF` и созданный путь совпадают, но не регистрируйте MCP URL в native-orchestrator. Сначала нужен реальный локальный прогон.

Результат шага: для нужного окружения подготовлены namespace и read-only-доступ будущего pod, а секреты созданы в `secrets/dynaconf/<ENV_FOR_DYNACONF>`. Пользователям навык ещё не виден.

## Шаг 9. Прогоните реальный сценарий локально через кастомную UI

Теперь замените mock/fake-клиенты реальными интеграциями и запустите навык у себя. Локальная кастомная UI должна обращаться напрямую к локальному HTTP/MCP-сервису, без native-orchestrator и chat-service.

Для локального запуска:

- перенесите только нужные значения секретов в локальный `.env`, который находится в `.gitignore`, либо используйте отдельный read-only Vault-токен, если такой режим уже настроен;
- не передавайте приложению редакторский токен от Vault;
- используйте те же несекретные URL и модель, которые будут заданы на стенде;
- после прогона очистите shell history от случайно вставленных значений и убедитесь, что `.env` не попал в Git.

Проверьте через кастомную UI реальный пользовательский сценарий:

1. Запустите сервис локально.
2. Откройте локальную UI и вызовите локальный MCP tool.
3. Для файлового навыка загрузите через S3 настоящую тестовую PDF-выписку с текстовым слоем.
4. Дождитесь извлечения текстового слоя и обезличивания в depermash.
5. Выполните реальный запрос в LLM через RouterAI.
6. Проверьте итоговый человекочитаемый ответ и обработку ошибок.

Не используйте фотографию документа, скан или PDF без текстового слоя как позитивный тест: текущий контур не выполняет OCR по изображению. Отдельно проверьте такой файл как негативный сценарий — пользователь должен получить объяснение, что нужен PDF или другой документ с выделяемым текстом.

Как убедиться, что сработала реальная LLM, а не заглушка:

- в безопасных логах есть факт внешнего LLM-вызова, название модели, статус и длительность;
- при намеренной подмене LLM-клиента тест возвращает другой контролируемый результат;
- ответ зависит от содержания тестового документа и не повторяет один стандартный текст;
- в логах при этом нет API-ключа, сырого документа и ПДн.

До завершения этого шага не создавайте MR регистрации в native-orchestrator. `chat-service` в рамках подключения навыка не изменяйте. Если реальная интеграция не работает, исправляйте сам сервис и его настройки, не занимая место в каталоге навыков.

Результат шага: навык локально прошёл реальный путь S3 → depermash → MCP → LLM и доказал, что выдаёт не заглушку. Теперь его можно разворачивать на review-стенде.

- проверьте совпадение имени секции и `name` в `SKILL.md`;
- проверьте, что MCP отдаёт resource и tool;
- посмотрите логи старта/discovery native-orchestrator;
- убедитесь, что проверяете deployment native-orchestrator, используемый согласованным общим стендом.

Результат шага: native-orchestrator обнаружил навык и может вызвать его tool.

## Шаг 13. Не изменяйте chat-service

На текущем этапе подключение нового MCP-навыка **не требует изменений в `l3m/backend/chat-service`**.
Не создавайте для этого ветку или MR в chat-service, не добавляйте карточку вручную и не меняйте
маршрутизацию на другой deployment оркестратора.

В частности, запрещено без отдельного архитектурного согласования менять:

- `ci_cd/values.yaml` и другие values-файлы chat-service ради подключения навыка;
- `orchestrator_client__base_url`;
- `orchestrator_client_v2__base_url`;
- `orchestrator_client_v2__stream_path`;
- `orchestrator_client_v2__summary_path`;
- ENV/Vault overrides этих параметров;
- общие маршруты, от которых зависят другие продукты.

На момент последней согласованной конфигурации в `chat-service/main` оба базовых URL сохранены на
общем адресе:

```yaml
orchestrator_client__base_url: "https://orchestrator.dv.gigalegal.tech"
orchestrator_client_v2__base_url: "https://orchestrator.dv.gigalegal.tech"
```

Не переключайте `orchestrator_client_v2__base_url` на отдельный native-orchestrator только ради
нового навыка. Такая правка однажды перенаправила общий трафик chat-service и сломала сервис ГПН,
который продолжал работать через обычный оркестратор. Изменение пришлось срочно откатить.

Для общего стенда новых навыков регистрация выполняется в согласованной ветке native-orchestrator
через MCP-блок в `src/common/config/orchestrator.toml`. Карточка навыка формируется на основании
`SKILL.md`, который отдаёт MCP-сервис.

Если навык зарегистрирован в native-orchestrator, но UI его не видит или не вызывает:

1. проверьте MCP URL, `SKILL.md`, tool и discovery native-orchestrator;
2. проверьте, что используется согласованный общий стенд и правильная ветка оркестратора;
3. зафиксируйте фактическое поведение и обратитесь к владельцам chat-service/стенда;
4. не исправляйте проблему самостоятельным переключением URL chat-service.

Результат шага: регистрация навыка выполнена без изменения общего chat-service и без риска нарушить
работу его существующих потребителей.

# Технический контекст для разработчика и LLM

Этот раскрывающийся раздел можно использовать как технический справочник или передать Claude, Codex либо другой LLM, которая помогает выполнить инструкцию. Если фактический код в актуальной ветке расходится с этим разделом, приоритет у кода текущего `main`: сначала исследуйте состояние репозиториев, затем вносите изменения.

## Общие правила для разработчика и LLM

- Не коммить, не пушить, не создавать MR и не менять внешние сервисы без прямого поручения пользователя.
- Не раскрывать значения Vault tokens, API keys, S3 tokens, kubeconfig, сертификатов, `.env` и ПДн ни в ответах, ни в логах, ни в diff.
- Не копировать секреты в TOML, Helm values, Dockerfile, CI config, тесты или документацию.
- Не удалять и не перезаписывать чужие локальные изменения. Перед правками проверять `git status`, текущую ветку, remote и diff.
- Для поиска использовать `rg`; список файлов также получать через режим перечисления файлов ripgrep. Перед копированием шаблона сверять его с актуальным `main` соответствующего репозитория.
- Разделять реализацию MCP-контракта и регистрацию MCP URL. Контракт нужен для локальных тестов; регистрация в native-orchestrator выполняется только после реального интеграционного прогона и появления доступного стендового URL.
- Не считать зелёный pipeline доказательством работоспособности сервиса. Всегда отдельно проверять `/health`, `/metrics`, `/mcp/` и реальный основной сценарий.
- Не выдавать технические имена полей, внутренний JSON, stack trace, названия ветвей пайплайна, `Path B`, `GAP`, `has_minor_owner` и подобные служебные признаки в пользовательском ответе навыка. Пользовательский результат должен быть лаконичным и человекочитаемым.

## Сквозная архитектура

Рабочий путь запроса:

`UI -> chat-service -> native-orchestrator -> MCP skill -> S3 or LLM -> native-orchestrator -> chat-service -> UI`

Файловый путь:

`UI -> chat-service -> s3_service -> извлечение текстового слоя -> depermash -> anonymized file_id -> MCP skill -> LLM`

Ответ навыка проходит обратно через chat-service, где при необходимости выполняется деобезличивание. Один и тот же идентификатор диалога должен связывать загрузку, сообщения и вызов навыка. В MCP он передаётся как `thread_id`; файлы текущего сообщения передаются как `file_ids`.

## Шаг 1: имена, доступы и карточка сервиса

До кода зафиксировать:

- `skill_id` в `snake_case`, например `my_skill`;
- repository name и `SERVICE_NAME`;
- Kubernetes namespace и hostname в `kebab-case`;
- приложение, порт, Dockerfile, Vault environment, MCP tool и группа Keycloak;
- нужны ли LLM, файлы, S3, depermash и другие внешние сервисы.

Одинаковый `skill_id` должен использоваться в `SKILL.md`, секции native-orchestrator и пользовательской группе. Не смешивать `my_skill`, `my-skill` и `my-skill-service`: заранее составить явное отображение имён.

Проверить SSH-доступ к GitLab и права чтения эталонов. Создание проекта, namespace, Vault policy и групп выполняют только уполномоченные люди.

## Шаг 2: создание сервиса из savva

Клонировать `savva`, затем переименовать исходный remote в `savva` и добавить новый `origin`, чтобы исключить случайный push в эталон.

Сохранить полезный каркас:

- `src/app` для HTTP, MCP и wiring;
- `src/agents` для бизнес-графа и LLM;
- `src/infrastructure` для внешних клиентов;
- `src/common` для конфигурации, ошибок, логов и метрик;
- `tests`, `Makefile`, `pyproject.toml`, `uv.lock`, Docker и CI.

Заменить все упоминания `etalon_service`, `savva`, старые ingress host, namespace, image path, module name и примеры ответов. После переименования выполнить `rg` по старым именам.

Не менять архитектурные границы без необходимости. В `savva` команда `make check` должна соответствовать CI и обычно включает Ruff, format check, mypy, pytest и import-linter.

## Шаг 3: Dynaconf, LLM, S3 и depermash без боевых секретов

Каноническая зависимость для Vault:

`dynaconf[vault]>=3.2.13`

Пример инициализации смотреть в `land_area/src/common/config/config.py`. Нужные свойства:

- `environment=True`;
- `load_dotenv=True`;
- TOML из `src/common/config/toml/*.toml`;
- `envvar_prefix=False`;
- вложенные ENV задаются через двойное подчёркивание, например `LLM__MODEL`.

Несекретные LLM-параметры для схемы RouterAI:

- `LLM__PROVIDER=openai`;
- `LLM__MODEL=<согласованная модель>`;
- `OPENAI_BASE_URL=https://routerai.ru/api/v1`.

Секрет LLM для совместимого с `land_area` шаблона:

- `OPENAI_API_KEY` содержит RouterAI key, несмотря на имя переменной.

Текущий `land_area` также умеет искать `ROUTER_AI_API_KEY` в своём environment, затем в Dynaconf environment `orchestrator`, затем использует `OPENAI_API_KEY`. Для нового навыка не создавать скрытую зависимость от environment оркестратора без согласованной Vault policy. Предпочитать собственный Vault path навыка и одно явно согласованное имя секрета.

Добавить fail-fast проверку настроек в lifespan. Для provider `openai` или `routerai` сервис не должен стартовать без base URL и ключа. Ошибка конфигурации не должна превращаться в пользовательский ответ «Недостаточно данных».

Для файлового навыка заранее определить:

- `S3_SERVICE_BASE_URL`;
- `S3_SERVICE_ACCESS_TOKEN` как секрет;
- `ANONYMIZER__BASE_URL`, только если сервис вызывает depermash напрямую;
- timeout, polling interval и deadline;
- интерфейс fake S3 client для unit-тестов.

В стандартном потоке depermash вызывается внутри S3, поэтому прямой anonymizer client навыку может не понадобиться. Не сохранять исходный файл или сырой текст в БД/на диск навыка. Не писать содержимое документа и ПДн в логи.

Текущее ограничение файлового контура: он извлекает только уже существующий текстовый слой. Фотографии, сканы и PDF без текстового слоя не являются поддерживаемым позитивным входом. PDF-выписки и документы с выделяемым текстом подходят. Для неподдерживаемого файла возвращать понятное сообщение, что нужен документ с текстовым слоем, а не «Недостаточно данных».

## Шаг 4: бизнес-логика

Держать HTTP/MCP transport отдельно от бизнес-сервиса. Бизнес-логика не должна зависеть от FastAPI request, Context FastMCP или глобального mutable state.

Рекомендуемые свойства:

- строгие Pydantic-модели входа и результата;
- dependency injection для LLM и внешних клиентов;
- детерминированные правила отдельно от генерации формулировок LLM;
- явные timeout, retry и error mapping;
- unit-тесты без реальных внешних API;
- человекочитаемый fallback, который не маскирует системную ошибку под отсутствие данных.

LLM не должна самостоятельно менять детерминированный юридический verdict. Если решение вычисляется правилами, модель только формулирует уже рассчитанный результат. Не копировать ограничения или fixture конкретного эталонного навыка, например фильтр по региону, если это не требование нового сервиса.

## Шаг 5: MCP-контракт без регистрации

Основные файлы-примеры:

- `land_area/src/app/mcp/server.py`;
- `land_area/src/app/mcp/runner.py`;
- `land_area/src/app/server/server.py`;
- `land_area/src/skills/land_area/SKILL.md`;
- `land_area/tests/integration/test_mcp.py`.

Использовать FastMCP и `SkillsDirectoryProvider`. Skills root обычно `src/skills`. Навык должен публиковать resource:

`skill://<skill_id>/SKILL.md`

Обязательные frontmatter-поля `SKILL.md`:

- `name`;
- `title`;
- `description`;
- `mode`, обычно `entrypoint`;
- `tool_name`, обычно `<skill_id>_invoke`.

`entrypoint` выбирать для навыка с одним основным tool, который сам формирует финальный ответ. `agentic` использовать только когда native-orchestrator должен управлять несколькими инструментами. Если `tool_name` указан, native-orchestrator по умолчанию интерпретирует навык как entrypoint. Явное поле `mode` предпочтительнее неявного поведения.

Практический шаблон из `land_area`:

- `FastMCP(name=<skill_id>, providers=[SkillsDirectoryProvider(...)])`;
- Pydantic request model;
- один async tool `<skill_id>_invoke`;
- `mcp.http_app(path="/", transport="http")`;
- mount приложения на `/mcp`;
- запуск lifespan FastMCP внутри lifespan FastAPI.

Если tool использует wrapper `data`, его JSON Schema должна корректно содержать поля внутри `data`. Защищённые поля контекста native-orchestrator:

- `thread_id`;
- `message_id`;
- `history_messages`;
- `file_ids`.

Оркестратор инжектирует эти поля сам и скрывает их от LLM-facing schema. Он передаёт `file_ids` только если tool schema объявляет это поле. Не заставлять модель выдумывать идентификаторы диалога или файлов.

MCP tool может отправлять прогресс через `ctx.info` или notifications. Финальный ответ должен быть терминальным и человекочитаемым. Не стримить сырые internal state, secret, Pydantic dump или stack trace.

В `land_area` MCP app монтируется на `/mcp`, а `API_ROOT` на стенде установлен в пустую строку. Неправильный `root_path` может дать 404 на MCP даже при живом `/health`.

Базовые команды:

- `make check`;
- `make run`;
- `curl -fsS http://localhost:8080/health`;
- запрос `/metrics`;
- FastMCP Client для `list_tools`, `list_resources`, `read_resource` и `call_tool`.

Не проверять MCP только обычным curl: discovery и tool call требуют MCP-клиента или integration test.

До запроса инфраструктуры должны работать:

- health и metrics;
- MCP discovery;
- чтение `SKILL.md`;

Локальная UI на этом этапе является временным dev-инструментом и обращается напрямую к локальному HTTP/MCP. Она не должна попадать в production runtime.

## Шаг 7: Docker, Helm и CI/CD

Сверять актуальные файлы `savva` и `land_area`:

- `.gitlab-ci.yml`;
- `ci_cd/dev/<service>.Dockerfile`;
- `ci_cd/run_scripts/start.sh`;
- `ci_cd/values.yaml`;
- `ci_cd/values-beta.yaml`.

Ожидаемый runtime сейчас Python 3.13. Установка через `uv sync` должна использовать зафиксированный lockfile и исключать dev dependencies. Образ должен копировать весь `src`, включая `src/skills`, запускаться не от root и слушать `PORT`, по умолчанию 8080.

Quality gates:

- Ruff lint;
- Ruff format check;
- mypy;
- pytest;
- import-linter.

Build обычно выполняется Kaniko после зелёных quality jobs. Deploy использует общий Helm chart. Проверять текущие registry, chart version, project id и CI variables в актуальном эталоне, потому что они могут измениться.

Helm values должны содержать service port, ingress, Vault/Dynaconf config, ServiceMonitor `/metrics`, health probes и `vaultToken: vault-token-for-dynaconf`.

Базовые Dynaconf values:

- `ENV_FOR_DYNACONF=<kebab-case skill env>`;

- `VAULT_KV_VERSION_FOR_DYNACONF=2`;
- `SETTINGS_FILES_FOR_DYNACONF` указывает на `/app/src/common/config/toml/*.toml`.

Если repository name содержит underscore, Helm release и hostname всё равно должны быть DNS-safe в kebab-case. Review hostname брать из deploy job, не угадывать.

## Шаг 8: DevOps и Vault

Обращаться к Дмитрию Тихонову только после базового локального прогона. Передать:

- service name;
- Kubernetes namespace;
- pod token с правами только чтения;
- environment `main` или `beta`.

- runtime pod token только читает секреты и подключается через Kubernetes Secret `vault-token-for-dynaconf`;
- editor token используется человеком для входа в Vault и никогда не передаётся приложению.

Vault DEV login:

`https://vault-dev.gigalegal.tech/ui/vault/auth?with=token`

Создать путь:

`secrets/dynaconf/<ENV_FOR_DYNACONF>`

Минимальные секреты для LLM плюс файлового навыка:

- `OPENAI_API_KEY`;
- `S3_SERVICE_ACCESS_TOKEN`.

RouterAI key выдаёт Евгений Добрецов при первом подключении Claude, Codex или RouterAI. S3 token при разрешённом доступе можно взять из Vault path `land-area`; значение не выносить из Vault в чаты или репозиторий. Если доступа нет, запросить его у DevOps.

Для `beta` доступы и path не считать автоматически совпадающими с `main`.

## Шаг 9: реальный локальный прогон

После Vault выполнить реальный сценарий через локальную custom UI, но ещё без регистрации в native-orchestrator. `chat-service` на этом и последующих этапах не изменять.

Для локального процесса использовать только нужные service secrets в gitignored `.env` или отдельный read-only Vault token. Не запускать приложение с editor token.

Проверить:

- реальный RouterAI call;
- реальный S3 call;
- извлечение текста и depermash;
- основной MCP tool;
- человекочитаемый результат;
- timeout и ошибки внешних сервисов;
- отсутствие secrets и ПДн в логах.

Безопасное доказательство реального LLM-вызова: в structured logs есть provider/model, status, duration и при наличии request id, но нет prompt, полного документа и API key. Ответ должен зависеть от содержания документа. Mock-клиент должен давать отдельно контролируемый тестовый результат.

S3 consumption для файлового навыка обычно использует:

`GET /s3/download/{file_id}/anonymized`

Обрабатывать:

- 200: готовый обезличенный текст;
- 202: обработка продолжается, poll до deadline;
- 404: файл не найден или неверный id;
- 422: извлечение/обезличивание не удалось.

Route names для upload/token могли изменяться. Перед реализацией сверять `s3_service/src/app/routers/s3.py`, `s3_service/docs` и актуальный клиент `land_area/src/infrastructure/s3/client.py`. Service token передаётся как Bearer и не выдаётся браузеру.

Позитивный тест выполнять на PDF с текстовым слоем. Фото или скан проверять как негативный сценарий с понятным объяснением ограничения.

## Шаг 10: review-стенд

Открыть MR навыка. Дождаться quality, build и deploy. Из deploy job извлечь фактические:

- ingress hostname;
- namespace;
- Helm release или instance name;
- image tag.

Проверить внешний `/health`, `/metrics`, MCP discovery и реальный tool call. Pod должен читать Vault своим read-only token. Если deploy зелёный, но health не отвечает, проверять pod startup, port mismatch, ingress, `API_ROOT`, Vault path и fail-fast settings validation.

Review URL является временным. Не оставлять его в постоянной конфигурации native-orchestrator.

## Шаг 11: pre-main очистка и main deploy

Перед merge навыка в `main`, включая merge после MCP-интеграционного теста, удалить из runtime:

- local UI и dev routes;
- mock/fake/stub clients и hardcoded responses;
- `localhost`, `127.0.0.1`, `host.docker.internal` и local ports;
- review URLs;
- `change-me`, `example` и другие placeholders;
- local `.env`;
- plaintext secrets.

LLM должна выполнить поиск минимум по runtime config, Docker, Helm и CI. Полезный паттерн поиска:

`rg -n 'localhost|127\\.0\\.0\\.1|host\\.docker\\.internal|change-me|example|mock|fake|stub' src ci_cd .gitlab-ci.yml`

Не удалять законные test fixtures автоматически. Сначала определить, попадают ли они в production image или runtime path.

Проверить effective configuration после наложения TOML, process ENV, Helm и Vault. Более приоритетный ENV может вернуть локальный URL, хотя TOML выглядит правильно.

Секреты остаются только в Vault. Несекретные main values должны указывать на реальные DEV services. `.env.example` может содержать placeholders только если он не загружается runtime и не используется как рабочая конфигурация.

До merge собрать production-like image, проверить health, MCP и один реальный вызов. После main deploy взять стабильный `INGRESS_HOST` из deploy job. Не угадывать URL.

## Шаг 12: native-orchestrator

Регистрация выполняется в:

`native-orchestrator/src/common/config/orchestrator.toml`

Для общего стенда новых навыков изменения вносятся в согласованную ветку
`feat/new_skiils_from_products`. Это не даёт разрешения менять маршрутизацию `chat-service/main`.

Секция:

`[default.orchestrator.mcp.<skill_id>]`

Поля:

- `url = "https://<stable-main-host>/mcp/"`;
- `add_orchestrator = true` для участия в автоматическом выборе;
- `add_orchestrator = false` для навыка, вызываемого только явно.

Использовать стабильный main URL. В текущей конфигурации discovery refresh interval равен примерно 300 секундам, heartbeat около 10 секунд, tool timeout около 600 секунд; перед диагностикой сверить актуальный config. После deploy native-orchestrator discovery может обновиться не мгновенно.

Проверка каталога:

`GET /orchestrator/skills?user_groups=<skill_id>`

Если навык не обнаружен:

- проверить `/mcp/` напрямую;
- проверить resource URI и frontmatter `name`;
- проверить `tool_name` и фактическое имя tool;
- проверить trailing slash URL;
- проверить логи discovery native-orchestrator;
- проверить, что user group совпадает с skill id;
- дождаться refresh или redeploy согласно процессу команды.

Native-orchestrator получает title и description из `SKILL.md`; отдельную UI-карточку в chat-service в текущем процессе не добавлять.

## Шаг 13: запрет изменений chat-service

Не добавлять карточку в `chat-service/src/common/config/toml/orchestrator_skills.toml` и не менять
`skills.toml`, values, ENV или Vault chat-service ради нового MCP-навыка.

Не изменять:

- `orchestrator_client__base_url`;
- `orchestrator_client_v2__base_url`;
- `orchestrator_client_v2__stream_path`;
- `orchestrator_client_v2__summary_path`.

Согласованные значения общего `chat-service/main` должны сохраняться, пока владельцы сервиса не
утвердят отдельную миграцию. Самостоятельное переключение `orchestrator_client_v2__base_url` на
другой native deployment меняет маршрут общего трафика, а не только нового навыка. Именно такое
изменение нарушило работу ГПН и потребовало срочного revert.

При проблеме интеграции проверять MCP backend, discovery и согласованную ветку native-orchestrator.
Если проблема действительно находится на границе chat-service, собрать диагностику и передать её
владельцам сервиса, не вносить маршрутную правку самостоятельно.

## Шаг 14: ACL

Тестовому пользователю нужна группа Keycloak/client-profile с точным именем `<skill_id>`. Имя должно совпадать в:

- `SKILL.md`;
- native-orchestrator TOML;
- user group.

Если skill виден администратору, но не обычному пользователю, сначала проверять ACL/group propagation, а не код навыка.

## Шаг 15: UI стенда коллег и E2E

Проверять полный путь клиента, а не только прямой MCP:

- пользователь видит карточку;
- skill выбирается явно или автоматически;
- history, `thread_id`, `message_id` и `file_ids` доходят корректно;
- progress events короткие и понятные;
- terminal response один и приходит последним;
- chat-service сохраняет ответ;
- depermash placeholders восстанавливаются корректно;
- пользовательский текст не содержит internal fields и JSON.

Для файла использовать один chat id от загрузки до вызова. Позитивный вход: PDF с текстовым слоем. Негативные входы: отсутствующий файл, неверный UUID, неподдерживаемый тип, фото/скан без текстового слоя, 202 timeout, 404 и 422.

Диагностировать по слоям:

1. skill `/health`;
2. skill `/mcp/` discovery и direct call;
3. native-orchestrator catalog и invocation logs;
4. согласованный стенд и общую маршрутизацию — только в режиме диагностики, без изменения chat-service;
5. user group;
6. S3 file id и chat id;
7. Vault effective config;
8. внешние LLM/S3/depermash calls.

## Типовые технические ошибки

- `404` на `/mcp/` при живом health: неверный mount, root path, ingress path или trailing slash.
- Навык отсутствует в catalog: MCP resource не соответствует `skill://<name>/SKILL.md`, frontmatter name не совпадает, tool отсутствует, URL недоступен или discovery ещё не обновился.
- Tool не получает files: поле `file_ids` отсутствует в JSON Schema tool или файлы привязаны не к текущему сообщению.
- Сервис падает при старте: Vault path не совпадает с `ENV_FOR_DYNACONF`, pod token не подключён, обязательный LLM key отсутствует, в main остался localhost.
- LLM всегда возвращает одинаковый fallback: проверить факт outbound call, key/base URL/model, timeout и exception mapping; не трактовать системную ошибку как отсутствие данных.
- S3 возвращает 202 бесконечно: установить deadline и понятный pending/timeout response.
- S3 возвращает 422 на фото: это ожидаемое текущее ограничение отсутствия OCR по изображению; попросить документ с текстовым слоем.
- Skill виден admin, но не пользователю: mismatch группы.
- Общий стенд не вызывает навык при рабочем MCP и discovery: зафиксировать используемый deployment и обратиться к владельцам стенда; не переключать `orchestrator_client_v2__base_url` самостоятельно.
- Deploy зелёный, но pod не ready: смотреть application startup logs, probe path, port, Vault и effective config.
