# Как развернуть навык на общем демо-стенде LegalOS

> Актуальный общий стенд новых навыков: <https://feat-skills-from-products.dv.gigalegal.tech/>.
>
> Регистрация выполняется в ветке `feat/new_skiils_from_products` репозитория
> `l3m/backend/native-orchestrator`. Для подключения MCP-навыка достаточно добавить его блок в
> `src/common/config/orchestrator.toml` и перезапустить pipeline/job этой ветки.
>
> Навык «Судебный приказ» используется ниже только как пример. Для другого навыка необходимо
> самостоятельно заменить `court_order`, URL MCP-сервиса, репозиторий, ветку и тестовые данные.

## Часть 1. Человекочитаемая инструкция

### Что мы получаем в результате

После развертывания:

- пользователь открывает <https://feat-skills-from-products.dv.gigalegal.tech/>;
- использует существующую UI и авторизацию общего стенда;
- загружает документ или пишет запрос;
- native-orchestrator стенда выбирает зарегистрированный навык;
- оркестратор обращается к отдельному MCP-backend навыка по HTTPS;
- результат возвращается пользователю в общей UI LegalOS.

Для нового навыка не нужно поднимать собственную UI, страницу авторизации, nginx или локальный
backend на сервере общего стенда. Backend навыка разворачивается отдельно штатным pipeline своего
репозитория, а общий стенд получает его MCP URL через конфигурацию оркестратора.

### Шаг 1. Соберите данные навыка

До регистрации зафиксируйте:

```text
SKILL_ID=<уникальное имя в snake_case>
TITLE=<название навыка>
SKILL_REPO=<URL репозитория навыка>
SKILL_BRANCH=<ветка с актуальным кодом>
MCP_URL=https://<домен-сервиса>/mcp/
HEALTH_URL=https://<домен-сервиса>/health
DATASET=<путь или ссылка на тестовые документы>
```

Для «Судебного приказа»:

```text
SKILL_ID=court_order
MCP_URL=https://court-order-service.dv.gigalegal.tech/mcp/
HEALTH_URL=https://court-order-service.dv.gigalegal.tech/health
```

`SKILL_ID` должен совпадать с именем MCP-навыка и не должен конфликтовать с уже зарегистрированными
секциями в `orchestrator.toml`.

### Шаг 2. Проверьте готовность backend навыка

До изменения native-orchestrator должны быть готовы:

- актуальный код навыка в согласованной ветке;
- успешные тесты и проверки качества, например `make check`;
- рабочий `/health`;
- рабочий MCP endpoint `/mcp/`;
- актуальный `SKILL.md` с названием, описанием и инструкцией выбора навыка;
- реальный вызов LLM, если навык использует LLM;
- рабочая файловая цепочка S3, OCR/извлечение текста и depermash, если навык принимает документы;
- секреты в согласованном Vault/окружении, а не в репозитории;
- отсутствие custom UI в production runtime навыка.

Общий стенд не должен использоваться для маскировки неготового backend.

### Шаг 3. Разверните backend навыка

Запустите штатный pipeline репозитория навыка и дождитесь успешного deploy. Backend должен получить
стабильный HTTPS MCP URL, доступный из контура общего native-orchestrator.

После deploy проверьте:

```bash
curl -fsS https://<домен-сервиса>/health
```

Ожидается HTTP 200 и штатный статус сервиса.

Одного `/health` недостаточно. MCP следует проверить MCP-клиентом или интеграционным тестом:

1. подключение к `/mcp/`;
2. discovery tools/resources;
3. чтение `SKILL.md`;
4. прямой вызов основного tool;
5. получение одного завершённого пользовательского ответа.

### Шаг 4. Откройте ветку общего оркестратора

Репозиторий:

<https://gitlab.gigalegal.space/l3m/backend/native-orchestrator>

Рабочая ветка общего стенда:

```text
feat/new_skiils_from_products
```

Файл регистрации:

<https://gitlab.gigalegal.space/l3m/backend/native-orchestrator/-/blob/feat/new_skiils_from_products/src/common/config/orchestrator.toml?ref_type=heads>

Если работа выполняется локально:

```bash
git clone https://gitlab.gigalegal.space/l3m/backend/native-orchestrator.git
cd native-orchestrator
git fetch origin
git switch feat/new_skiils_from_products
git pull --ff-only origin feat/new_skiils_from_products
git status
```

Перед изменениями рабочая директория должна быть чистой.

### Шаг 5. Добавьте три строки регистрации навыка

Откройте:

```text
src/common/config/orchestrator.toml
```

Добавьте отдельный блок:

```toml
[default.orchestrator.mcp.<skill_id>]
url = "https://<домен-сервиса>/mcp/"
add_orchestrator = true
```

Пример для «Судебного приказа»:

```toml
[default.orchestrator.mcp.court_order]
url = "https://court-order-service.dv.gigalegal.tech/mcp/"
add_orchestrator = true
```

Значение `add_orchestrator = true` означает, что навык участвует в автоматическом выборе
оркестратора. `title` и `description` в TOML добавлять не нужно: актуальная карточка загружается с
MCP-сервера из `SKILL.md`.

Не меняйте URL и флаги существующих навыков, если это не входит в отдельную согласованную задачу.

### Шаг 6. Проверьте изменение

Минимальные проверки:

```bash
git diff -- src/common/config/orchestrator.toml
git diff --check
PYTHONPATH=src uv run pytest tests/ -q
PYTHONPATH=src uv run ruff check src/
```

Если в репозитории появился новый обязательный gate, используйте актуальные команды из `AGENTS.md`,
`README.md` и CI.

Проверьте, что:

- добавлена только секция нового навыка;
- `skill_id` уникален;
- MCP URL заканчивается на `/mcp/`;
- endpoint отвечает из требуемого контура;
- в diff нет токенов, паролей и стендовых секретов.

### Шаг 7. Отправьте изменение в ветку и перезапустите job

Закоммитьте только изменение регистрации:

```bash
git add src/common/config/orchestrator.toml
git commit -m "feat: register <skill_id> on skills stand"
git push origin feat/new_skiils_from_products
```

Откройте pipeline ветки/MR в GitLab и перезапустите предусмотренную для стенда цепочку сборки и
deploy. В текущем native-orchestrator это jobs `build` и `agent:install`; ориентируйтесь на актуальные
названия jobs в pipeline.

Если job завершилась ошибкой, не запускайте многократные изменения конфигурации вслепую. Сначала
проверьте лог: доступность MCP URL, синтаксис TOML, сборку образа и deploy оркестратора.

### Шаг 8. Проверьте общий стенд

Откройте:

<https://feat-skills-from-products.dv.gigalegal.tech/>

Проверьте:

1. карточка навыка появилась в списке доступных навыков;
2. название и описание соответствуют `SKILL.md`;
3. текстовый запрос маршрутизируется в новый навык;
4. для файлового навыка загружается поддерживаемый формат документа;
5. выполняется реальная цепочка S3/OCR/depermash/LLM, если она предусмотрена;
6. пользователь получает один финальный ответ без внутренних JSON, токенов, stack trace и
   технической диагностики;
7. один существующий навык продолжает работать после изменения.

Если карточка появилась, но вызов не работает, сначала проверяйте MCP backend и его логи. Наличие
карточки подтверждает discovery, но не гарантирует успешную обработку запроса.

### Шаг 9. Прогоните согласованный датасет

До передачи стенда коллегам:

- прогоните согласованный набор документов;
- сохраните пользовательский ответ по каждому документу;
- проверьте поддерживаемые форматы файлов;
- проверьте отрицательные сценарии;
- убедитесь, что ответы не содержат масок обезличивания, секретов, внутренних endpoint и служебных
  статусов;
- не включайте в пользовательский отчёт SHA, duration, OCR wait и технические статусы.

Если UI-тестирование оставлено владельцу навыка, агент выполняет полную backend-проверку и передаёт
ссылку на стенд для ручной UI-приёмки.

### Шаг 10. Последующие обновления

Если код навыка изменился, но его публичный MCP URL остался прежним:

1. разверните новую версию backend из репозитория навыка;
2. проверьте `/health` и прямой MCP-вызов;
3. повторно проверьте навык на общем стенде.

Менять `orchestrator.toml` и перезапускать native-orchestrator в этом случае обычно не требуется.

Если изменились `skill_id`, MCP URL или участие в автоматическом выборе, обновите соответствующий
трёхстрочный блок в `feat/new_skiils_from_products` и снова запустите pipeline стенда.

### Шаг 11. Откат

Если новая регистрация нарушила работу общего стенда:

1. убедитесь, что проблема вызвана именно новой секцией;
2. выполните revert коммита регистрации либо верните предыдущие три строки;
3. отправьте revert в `feat/new_skiils_from_products`;
4. повторно запустите deploy job этой ветки;
5. проверьте существующие навыки и новый навык отдельно;
6. сохраните логи сбоя для диагностики.

Не откатывайте весь native-orchestrator и не меняйте `chat-service/main` ради ошибки одного навыка.

### Шаг 12. Передайте результат

Владелец навыка получает:

- ссылку на общий стенд;
- ссылку на pipeline регистрации;
- репозиторий, ветку и commit backend навыка;
- commit с регистрацией в native-orchestrator;
- результаты прогона датасета;
- список известных ограничений;
- способ точечного отката.

Отдельные логины создаются только по согласованной процедуре владельцев общего стенда. Не добавляйте
собственную страницу авторизации и не храните пароли в репозитории или инструкции.

## Часть 2. Техническая инструкция для LLM/агента

### 0. Цель и границы

Цель: подключить один готовый MCP-навык к общему стенду
`https://feat-skills-from-products.dv.gigalegal.tech/` через ветку
`native-orchestrator/feat/new_skiils_from_products`.

Обязательные ограничения:

- полностью прочитать `AGENTS.md`, `README.md` и инструкции навыка до изменений;
- начать с read-only-аудита backend навыка и native-orchestrator;
- не выводить `.env`, Vault, токены, cookies, пароли и приватные ключи;
- не изменять `chat-service/main` для регистрации навыка на этом стенде;
- не добавлять custom UI, nginx, standalone auth или локальные серверные адаптеры;
- не менять конфигурацию существующих навыков;
- не коммитить и не пушить без разрешения пользователя;
- не считать `/health` достаточной проверкой MCP;
- иметь точечный план revert до deploy.

### 1. Зафиксировать параметры

```text
STAND_URL=https://feat-skills-from-products.dv.gigalegal.tech/
ORCHESTRATOR_REPO=https://gitlab.gigalegal.space/l3m/backend/native-orchestrator.git
ORCHESTRATOR_BRANCH=feat/new_skiils_from_products
ORCHESTRATOR_CONFIG=src/common/config/orchestrator.toml
SKILL_ID=<snake_case>
SKILL_REPO=<git URL или локальный путь>
SKILL_BRANCH=<актуальная ветка>
MCP_URL=https://<service-domain>/mcp/
HEALTH_URL=https://<service-domain>/health
DATASET=<путь>
```

### 2. Проверить backend навыка

Исследовать репозиторий:

```bash
git status --short --branch
git remote -v
git log -1 --oneline
rg --files
rg -n 'localhost|127\.0\.0\.1|host\.docker\.internal|change-me|mock|fake|stub' \
  src ci_cd .gitlab-ci.yml
```

Совпадения в тестах не считать автоматически ошибкой. Определить, используются ли они в runtime.

Запустить полный gate проекта, например:

```bash
make check
```

Проверить после deploy:

```text
GET HEALTH_URL -> 200
MCP connect/discovery -> success
MCP read SKILL.md -> success
MCP основной tool -> один финальный пользовательский ответ
```

Для файлового навыка подтвердить реальную цепочку:

```text
файл -> platform S3 -> OCR/извлечение текста -> depermash
     -> anonymized file_id -> MCP backend -> RouterAI/LLM -> ответ
```

### 3. Проверить ветку оркестратора

```bash
git fetch origin
git switch feat/new_skiils_from_products
git pull --ff-only origin feat/new_skiils_from_products
git status --short --branch
rg -n '^\[default\.orchestrator\.mcp\.' src/common/config/orchestrator.toml
```

Stop conditions:

- рабочая директория содержит чужие изменения;
- секция `SKILL_ID` уже существует с другим URL;
- MCP URL не отвечает;
- `SKILL.md` отсутствует или не соответствует навыку;
- нет подтверждения на изменение и push.

### 4. Добавить регистрацию

В `src/common/config/orchestrator.toml` добавить ровно одну секцию:

```toml
[default.orchestrator.mcp.<skill_id>]
url = "<MCP_URL>"
add_orchestrator = true
```

Не добавлять `title` и `description`: native-orchestrator получает их из `SKILL.md` MCP-сервера.

Перед commit проверить:

```bash
git diff -- src/common/config/orchestrator.toml
git diff --check
PYTHONPATH=src uv run pytest tests/ -q
PYTHONPATH=src uv run ruff check src/
```

### 5. Commit, push и deploy

Только после разрешения пользователя:

```bash
git add src/common/config/orchestrator.toml
git commit -m "feat: register <skill_id> on skills stand"
git push origin feat/new_skiils_from_products
```

В GitLab открыть pipeline ветки/MR и выполнить предусмотренные jobs сборки и deploy. Для текущей
конфигурации native-orchestrator проверить `build`, затем `agent:install`.

Не считать pipeline успешным только по статусу build: нужен успешный deploy job и последующая
проверка стенда.

### 6. Сквозная проверка

Проверить:

```text
[ ] MCP backend health = 200
[ ] MCP discovery успешно
[ ] SKILL.md читается
[ ] карточка появилась на STAND_URL
[ ] явный выбор нового навыка работает
[ ] автоматический выбор работает при add_orchestrator=true
[ ] файловая цепочка работает, если применимо
[ ] финальный ответ не содержит секретов и технической диагностики
[ ] существующий навык продолжает отвечать
[ ] согласованный датасет пройден
```

### 7. Rollback

Если проблема вызвана регистрацией:

1. выполнить revert только коммита, добавившего секцию навыка;
2. push revert в `feat/new_skiils_from_products`;
3. повторно выполнить deploy job;
4. проверить каталог и существующие навыки.

Если регистрация работает, а обработка падает внутри tool, не менять оркестратор: диагностировать и
исправлять backend навыка.

### 8. Финальный отчёт

Сообщить пользователю:

- URL общего стенда;
- commit регистрации;
- pipeline и deploy status;
- фактически проверенный MCP URL без секретных query-параметров;
- результат backend и сквозной проверки;
- результат датасета;
- ограничения и точный rollback.

Не включать в пользовательский отчёт токены, содержимое Vault, raw `.env`, ПДн, внутренний OCR-текст,
служебный JSON и stack trace.
